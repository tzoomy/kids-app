# ארכיטקטורה ומפת דרכים — אפליקציית הלמידה לבנות

סטטוס: **הצעה — ממתין לאישור**. המסמך מתאר כיוון טכני ומבני לגרסה הבאה. הוא אינו משנה את האפליקציה החיה בכתובת [מסעדת החיות](https://tzoomy.github.io/kids-app/). בחירות שמאור טרם אישר מסומנות במפורש.

המסמך נשען על `vision-summary.md` ועל `gpt-research-plan.md` (מחוץ למאגר, בתיקיית העבודה). דרישות הליבה שכבר נקבעו: מענה לשתי הבנות (כיום בנות 2 ו־5), ממשק בעברית, לימוד אנגלית וחיזוק צרפתית, טאבלט Android כמכשיר עיקרי, צבירת זמן פנאי מפעילות חינוכית, אזור הורה, הנאה מהתוכן החינוכי עצמו, עבודה ללא רשת, איסוף נתונים מינימלי, ואי שימוש בשירותים בתשלום בזמן הריצה.

האב־טיפוס הנוכחי הוא דף HTML/JS אחד עם אימוג'י, TTS של המכשיר, ושמירה ב־`localStorage`. הוא מוכיח את הלולאה הבסיסית (פרופיל ← משחק ← צבירה ← פנאי ← הורה), אבל אינו מתאים לגרפיקה ואנימציות ברמה גבוהה או להוספת עולמות בלי לשכתב את הקוד בכל פעם.

## 1. מחסנית טכנולוגית

**הצעה — ממתין לאישור:** Vite + TypeScript + Phaser 3, כ־PWA סטטית שמתפרסמת ל־GitHub Pages.

| שכבה | בחירה מוצעת | נימוק |
|---|---|---|
| מנוע משחק | Phaser 3 | מיועד למשחקי דפדפן: סצנות, ספרייטים, אנימציות, גרירה, פיזיקה בסיסית ואודיו. נשאר אפליקציית ווב שמוסיפים למסך הבית, בלי חנות ובלי שירות בתשלום. |
| שפה וכלי בנייה | TypeScript + Vite | טיפוסים למנוע הפנאי, לתוכן JSON ולסצנות; בנייה מהירה; פיצול קוד לפי עולם; פלט סטטי ל־Pages. |
| ממשק מעטפת | HTML/CSS קטן מחוץ לקנבס, או DOM בתוך Phaser | ניווט עברי, אזור הורה וטפסים נוחים יותר ב־DOM; המשחקים עצמם על הקנבס. |
| PWA | `vite-plugin-pwa` (Workbox) | מטמון נכסים לעבודה ללא רשת, מניפסט בעברית, אייקונים, `standalone`. |
| בדיקות | Vitest + Playwright | יחידות למנוע הפנאי ותוכן; צילומי מסך בגודל טאבלט בכל PR. |
| פרסום | GitHub Actions → GitHub Pages | בנייה מ־`main` (או מתגית), העלאת תיקיית `dist` בלבד. חינמי, בלי שרת ובלי ספק אחסון נוסף. |

חלופות שנשקלו ונדחו לפי שעה (גם הן **הצעה — ממתין לאישור**):

- להמשיך ב־HTML/JS טהור: מהיר לאב־טיפוס, חלש לאנימציה, לאטלסים ולמשחקי גרירה.
- PixiJS בלבד: ציור מצוין, אבל בלי סצנות, פיזיקה וקלט מוכנים; נבנה יותר קוד בעצמנו.
- Godot / Unity לייצוא ווב: כבד יותר לצוות CLI, פחות טבעי לתוכן JSON ול־PWA קלילה, וקשה יותר לסקירת PR.
- Capacitor / אפליקציית חנות: יעד עתידי אפשרי, לא נחוץ כל עוד הטאבלט פותח את האתר ומוסיף אותו למסך הבית.

המעבר יתבצע בענף נפרד, בלי לשבור את האתר החי עד שאישור ומיזוג. עד אז קבצי האב־טיפוס נשארים בשורש המאגר, כפי שהם היום.

### פרסום מוצע

```
PR מאושר → מיזוג ל-main → GitHub Action
  (npm ci, בדיקות, vite build)
  → העלאת dist ל-GitHub Pages
```

**הצעה — ממתין לאישור:** לאחר המעבר, Pages יוגדר לפרסום מתוצר ה־Action ולא משורש `main`. כתובת המשחק תישאר `https://tzoomy.github.io/kids-app/`. יש לקבוע `base: '/kids-app/'` ב־Vite. שינוי מקור הפרסום הוא פעולת הגדרות במאגר, ודורש אישור וביצוע של מאור (או מי שיש לו הרשאת admin). לפני ההחלפה בכתובת החיה יש לבדוק build ב־preview (למשל Pages של הענף, או הפעלה מקומית של `dist`). אם הפרסום הראשון נשבר, חוזרים זמנית לפרסום משורש `main` שבו נשמר האב־טיפוס, או ל־commit האחרון שעבד. המאגר ציבורי; אין לשים בו מפתחות, שמות אמיתיים של הבנות, או נתוני שימוש.

**מטמון PWA (עודכן אחרי הסקירות):** precache רק לשלד האפליקציה (HTML, JS של הליבה כולל Phaser, CSS, אייקונים, תוכן המינימום למשחק הדגל אם הוא חלק מהעלייה הראשונה). נכסי עולמות, אטלסים וקולות — runtime caching או טעינה יזומה בכניסה לעולם, כדי שההתקנה הראשונה לא תנסה להוריד את כל הספרייה. אחרי שנכס ירד פעם אחת, הוא זמין ללא רשת. חסר גם מנגנון עדכון: ב־PWA במצב `standalone` הקאש עלול להשאיר גרסה ישנה; **הצעה — ממתין לאישור** להציג להורה באנר רענון פשוט, בלי `skipWaiting` אלים באמצע משחק.

הערה על פיצול קוד: חבילת Phaser עצמה מגיעה כבר בכניסה (בסדר גודל של מאות קילובייטים אחרי gzip). החיסכון החשוב הוא בנכסים לפי עולם, לא בפיצול JS של כמה קילובייטים של לוגיקת משחק.

**הצעה — ממתין לאישור.** המבנה יופיע בענף המימוש, לא בפריסת האב־טיפוס הנוכחית.

```

  src/
    main.ts
    game/                # יצירת Phaser.Game, הגדרות סצנות
    core/
      leisure/           # מנוע צבירת הפנאי — מודול משותף, בלי תלות ב־Phaser
      storage/           # פרופילים, הגדרות הורה, התקדמות
      audio/             # TTS כעת, קבצי קול מוקלטים בהמשך, SFX

      restaurant/        # מסעדת החיות (המשחק הראשון למיגרציה)
```

## 3. מפת עולם, תבנית משחק, ותוכן כנתונים

**הצעה — ממתין לאישור.** פירוט העולמות והמשחקים ב־`docs/WORLDS.md`.

שלוש שכבות נפרדות:

1. **מפת העולם** — סצנה אחת שבה הילדה בוחרת אזור (בית השפות, גינת המספרים, מעבדת הטבע, סטודיו יצירה, ופינת פנאי מאושרת). הכניסה לעולם מציגה כמה משחקים. המפה משותפת לשתי הבנות; מה שמשתנה הוא מסלול האינטראקציה, מספר הבחירות, וההדרכה.
2. **תבנית משחק** — קוד כללי לסוג פעולה: בחירה בין פריטים, גרירה והנחה, מיון למדפים, רצף צעדים, יצירה חופשית. התבנית יודעת להציג דמות, להשמיע בקשה, לקבל פעולה, לתת משוב, ולדווח למנוע הפנאי ולמעקב הלמידה.
3. **תוכן כנתונים** — JSON לכל משחק: מיומנות, שפת לימוד, פריטים, משפטים, רמות, אילו פעילויות מזכות בפנאי, וקישורים לנכסי גרפיקה וקול. הוספת מאכלים, מילים או שלב חדש נעשית בקובץ התוכן.

סקיצה לתוכן (לא סופית; עודכנה אחרי הסקירות). המשפטים בשפות הלימוד נשמרים שלמים ומאושרים, ולא מורכבים בקוד משם עצם ומין דקדוקי בלבד — במיוחד בצרפתית (יידוע, partitif, `l'orange`). לפריטים יש תכונות (צבע, גודל) כשהמשחק צריך אותן. הסכימה תוגדר ב־TypeScript ותאומת ב־CI (למשל ב־Zod) לפני כל build, כדי שקובץ תוכן שבור לא יעלה ל־Pages.

```json
{
  "id": "animal-restaurant",
  "world": "language-house",
  "template": "choice-or-build-order",
  "skill": "listen-and-choose-food",
  "languages": ["en", "fr"],
  "earnsLeisure": true,
  "profiles": {
    "age2": { "choices": 2, "counts": [1], "hints": "demonstrate" },
    "age5": { "choices": 3, "counts": [1, 2, 3], "hints": "repeat-then-demonstrate" }
  },
  "items": [
    {
      "id": "apple",
      "he": "תפוח",
      "attributes": { "color": "red" },
      "sprite": "foods/apple",
      "audio": { "en": "audio/en/apple.ogg", "fr": "audio/fr/pomme.ogg" },
      "prompts": {
        "en": "I want an apple, please!",
        "fr": "Je voudrais une pomme, s'il te plaît !"
      }
    }
  ]
}
```

עקרונות תוכן:

- שפת לימוד אחת לכל סיבוב, עם כפתור עזרה בעברית.
- התקדמות נשמרת לפי מיומנות ושפה, לא כציון כללי אחד.
- חזרה מזכה לפי כללים, אבל לא בלי הגבלה על אותו שלב קל.
- אין כישלון מעניש: טעות מביאה רמז או הדגמה, לא הורדת יתרת פנאי.
- בשלב הראשון מאור והצוות עורכים JSON; כלי עריכה ידידותי להורה הוא יעד מאוחר, לא תנאי לפיילוט.

## 4. i18n ו־RTL

**הצעה — ממתין לאישור.**

- מעטפת האפליקציה, הניווט, אזור ההורה וההסברים: עברית, `dir="rtl"`, `lang="he"`.
- מחרוזות מעטפת בקובצי i18n (לפחות `he`), כדי לא להטמיע טקסט בקוד. אין דרישה כרגע לממשק באנגלית או בצרפתית.
- **כלל מוצע (עודכן אחרי הסקירות) — ממתין לאישור:** אין לרנדר משפטים בעברית או טקסט דו־כיווני ב־`Phaser.GameObjects.Text` על הקנבס. ל־Canvas `fillText` יש באגים ידועים ב־BiDi בכרום ב־Android. טקסט UI והוראות יוצגים בשכבת HTML/CSS מעל הקנבס (מעטפת או `DOMElement`). על הקנבס נשארים גרפיקה, ומילים בודדות ב־LTR בשפת הלימוד בלבד אם צריך.
- תוכן הלימוד באנגלית ובצרפתית מוצג בבידוד כיווניות (`dir="ltr"` / isolate) בשכבת ה־DOM.
- **הצעה — ממתין לאישור** למצב סקייל: `Phaser.Scale.FIT` עם letterbox, ללנדסקייפ ולפורטרט, בלי לחתוך כפתורים. כפתורי יציאה ועזרה לא יושבים על שולי המסך, כדי לא להתנגש במחוות המערכת של Android (חזרה, וילון התראות).
- פונטים: משפחת גופנים אחת שתומכת היטב בעברית ובאותיות לטיניות, נארזת באפליקציה כדי לעבוד ללא רשת. **הצעה — ממתין לאישור:** גופן חופשי עם רישיון ברור (למשל משפחת Noto), בלי גופנים בתשלום.
- כפתורים, מטרות מגע ואזורי גרירה גדולים; אין להסתמך על קריאה אצל בת השנתיים — הקול מוביל, הטקסט תומך. יש לטפל בלחיצות חוזרות, multi-touch ויד שמונחת על המסך (palm), ולנעול קלט בזמן משוב קצר.

## 5. אסטרטגיית שמע

**הצעה — ממתין לאישור.**

שלב א׳ היה, באב־טיפוס, Web Speech API. הסקירות מזהירות שזה שביר בטאבלטי Android: קול צרפתי או עברי עלול להיות חסר לאוף־ליין, `getVoices()` ריק בטעינה, ו־`speak()` לפעמים נכשל בשקט. לבת השנתיים מסך דומם הוא כשל חווייתי, לא רק בעיית איכות. גם כשיש קול, המבטא או המין הדקדוקי עלולים להיות שגויים.

**הצעה מעודכנת — ממתין לאישור:** כבר במיגרציית מסעדת החיות לארוז קובצי קול סטטיים (`.ogg`/`.mp3`) לכל משפט לימודי, שנוצרו בפיתוח (הקלטה אנושית אם אפשר, או TTS איכותי במחשב הפיתוח כגישור). כך המשחק עובד ללא רשת ואיכות הצרפתית לא תלויה במכשיר. הקלטות משפחתיות או מקצועיות נשארות יעד איכות, ולא חייבות לחכות לסוף כל העולמות. אם מאור יעדיף להישאר עם TTS המכשיר בשלב הראשון — חייבים גיבוי טקסט + אנימציית פה (ספרייטים של פה, לא רק tween של גודל), ובדיקה בטאבלט המשפחה.

אחרי המגע הראשון מחממים את מערכת השמע כדי להקטין השהיה. זמן האזנה והסתכלות באנימציה נחשב השתתפות, לא idle.

SFX קצרים (הצלחה, רמז, מעבר) יכולים להישאר סינתטיים או קבצים קטנים כבר בשלב א׳.

מדיניות: אין שליחת קול הילדה לשרת, אין תמלול, ואין AI בזמן אמת בצד הלקוח כדרישה. שימוש ב־AI מותר בפיתוח ובהפקת נכסים, לא בשימוש החי של הילדה, אלא אם מאור יחליט אחרת.

## 6. צינור גרפיקה ואנימציה

**הצעה — ממתין לאישור.**

כיוון סגנון (לבחירת מאור): איור חם ועגול לילדים, צבעים רוויים בניגודיות גבוהה, קו ברור, פנים ידידותיות, בלי דמויות מוגנות בזכויות יוצרים ובלי עומס פרטים ברקע. אותו סגנון לכל העולמות, עם פלטה שונה לכל אזור.

צינור עבודה מוצע:

1. מגדירים גיליון סגנון קצר (דמות, רקע, חפץ, אייקון) ודוגמאות ייחוס.
2. מייצרים נכסים בעזרת כלי AI לפי גיליון דמות קבוע, ואז בודקים אחידות, קריאות במסך טאבלט, ורגישות תרבותית. כלי AI מתקשים לשמור על אותה דמות בזוויות ובהבעות שונות עם רקע שקוף; לכן נדרשת עריכה ידנית, ואין להניח ש־"צינור AI" מייצר לבד סט מוכן למשחק. בודקים גם שאין דמיון בעייתי לדמויות מוגנות.
3. חותכים לספרייטים בגדלים קבועים, ומרכיבים texture atlas (למשל בעזרת כלי חופשי) כדי לצמצם טעינות. **הצעה:** גודל אתלס מקסימלי 2048×2048, כדי להקטין קריסות WebGL בטאבלטים חלשים. ביציאה מעולם משחררים טקסטורות (`textures.remove` / destroy), לא רק מסתירים סצנה.
4. שומרים מקורות (PNG/SVG) בנפרד מהאטלסים שבבנייה.
5. מנפישים קודם ב־Phaser Tweens (כניסה, נדנוד, הגשה). אנימציית פה או הבעות דורשות פריימים (frame animation), לא רק שינוי גודל. Lottie מתאים למעברי UI קצרים. Spine או חלופה קלת משקל — רק אם יופיע צורך בדמויות עם שלד; זה יעד מאוחר, לא חובה למשחק הראשון.

יעדי ביצוע לגרפיקה: אתלס לדמות ולחפצי המשחק, רקע אחד או שניים לכל סצנה, הימנעות מתמונות ענק ב־PNG לא דחוס. פורמט מוצע: WebP או PNG מותאם, עם גיבוי.

## 7. מנוע זמן הפנאי — מודול משותף

זהו רכיב ליבה שכבר נקבע כדרישה. פרטי הכללים עדיין **הצעה — ממתין לאישור**.

המודול (`src/core/leisure`) אינו תלוי ב־Phaser. כל משחק מדווח לו: התחלת פעילות, פעולה, השהיה, יציאה, סיום. הוא מחשב זמן השתתפות מזכה, יתרה, תקרות ומימוש, ושומר בנפרד ראיות למידה (מיומנות, שפה, הצלחה עצמאית או עם רמז).

כללים מוצעים, בהתאם למסמכי החזון (לא מדיניות סופית):

- הצבירה לפי השתתפות, כולל חשיבה, טעויות ורמזים; לא לפי מהירות או הצלחה.
- מסך ברקע, נעילה, או היעדר אינטראקציה ארוך אינם מזכים. משך ה־idle נבדק כדי לא לפגוע בילדה שחושבת.
- אין קנס על טעות, אין העברת יתרה בין אחיות, אין דירוג ביניהן.
- ההורה קובע לכל פרופיל: פנאי בסיסי, יחס המרה, תקרת צבירה, תקרת מימוש, תקרת יתרה, ותקרה כוללת ליום.
- באב־טיפוס נקבעו זמנית 10 דקות למידה תמורת 5 דקות פנאי, ותקרת צבירה של 30 דקות. אלה ערכי ברירת מחדל זמניים בלבד.
- יצירה מזכה רק אם סומנה כך בתוכן; פנאי עצמו אינו מייצר זכאות חדשה.
- מעבר יום: חצות לפי שעון המכשיר המקומי. יתרה שלא מומשה נשמרת עד תקרת היתרה, ומימוש למחרת כפוף לתקרות אותו יום (כפי שהוצע במסמך החזון). אין פקיעה מלחיצה.
- האזנה להוראה ואנימציה של המשחק אינן idle. סף ה־idle עצמו, ושוני אפשרי בין גיל 2 לגיל 5, **הצעה — ממתין לאישור** (באב־טיפוס: 20 שניות בלי מגע).
- כשנגמר זמן הפנאי באמצע פעילות, **הצעה — ממתין לאישור:** לא חוטפים את המסך מיד; נותנים לסיים פעולה קצרה או יצירה פתוחה (grace period), עם התראה רגועה מראש, ואז חוזרים למפה או לסיום.
- מגבלות ידועות: איפוס או שינוי שעון המכשיר יכול להשפיע על תקרות יומיות; האפליקציה לא יכולה להגן מפני זה במלואה ב־PWA. ניקוי נתוני האתר או הסרת ה־PWA מוחק התקדמות ויתרות עד שיהיה ייצוא.

ג׳מיני הציע לפשט ל־3 פרמטרים הוריים בלבד. המודל המפורט נשמר כהצעה כי כך תואר בחזון, אבל מסך ההורה חייב להישאר פשוט: אפשר להציג יחס ותקרה יומית, ואת השאר כברירות מחדל מתקדמות. מאור יכריע.

בדיקות יחידה יכסו המרה, תקרות, מעבר יום, idle מול האזנה, grace period, וחזרה על אותה פעילות.

## 9. אחסון, פרטיות ועבודה ללא רשת

**הצעה — ממתין לאישור.**

- כל הנתונים נשארים במכשיר. בלי חשבון, בלי אנליטיקה חיצונית, בלי סנכרון ענן בגרסה הראשונה. לוג שגיאות שנשלח החוצה אינו חלק מהתוכנית. לוג מקומי שמוצג להורה הוא רעיון פתוח, **הצעה — ממתין לאישור**, ולא יופעל בלי החלטה.
- אחסון מוצע: `localStorage` להגדרות ויתרות קטנות, ו־IndexedDB אם ניגשים ליצירות (ציורים) או ליומן אירועים ארוך. לכל מבנה נתונים יהיה מספר סכימה וקוד מיגרציה, כדי שעדכון משחק לא ישבור יתרה קיימת. ייצוא/ייבוא ידני לקובץ יכול להגיע בהמשך לגיבוי בין מכשירים; עד אז מחיקת נתוני כרום היא סיכון ידוע, ויש לציין זאת לאזור ההורה.
- ה־Service Worker שומר את השלד, ואחר כך את הנכסים שכבר ירדו. משחק שהורד פעם אחת אמור לעבוד בלי רשת.
- קול סטטי שנארז עם התוכן הוא הבסיס לאוף־ליין אמין; TTS מכשיר אינו מספיק לכך.
- המאגר הציבורי מכיל רק קוד, תוכן משחק ונכסים מקוריים. אין בו נתוני שימוש.

## 10. בדיקות

**הצעה — ממתין לאישור.**

- Vitest: מנוע פנאי, טעינת JSON, אימות סכימה, בחירת רמה לפי פרופיל, כללי חזרה, i18n בסיסי.
- Playwright: מסע קצר (בחירת פרופיל, כניסה למשחק, אזור הורה) על גודל טאבלט. **הצעה:** 1280×800 ו־800×1280 (לנדסקייפ ופורטרט), עם צילומי מסך כ־artifacts בכל PR. בהמשך אפשר להוסיף מכשיר אמיתי או הדמיית Android.
- צילומי Phaser ב־CI (Ubuntu, בלי GPU) עלולים להיות לא יציבים ב־WebGL/SwiftShader, או להצטלם לפני סיום טעינה. **הצעה:** לחשוף במצב בדיקה דגל כמו `window.__GAME_READY__` אחרי פריים יציב, להמתין לפונטים ולטקסטורות, לקבוע סף סבילות לרגרסיה חזותית, ובמידת הצורך להריץ את ה־CI ב־Canvas 2D.
- בדיקת e2e אחת לפחות לאוף־ליין (שלד + נכסים שכבר במטמון), כי זו דרישת ליבה.
- בדיקות לא מודדות "האם הילדה למדה", אלא שהמשחק לא נשבר, שהצבירה נכונה, וששינוי גרפי נראה בסקירה.
- CI רץ על כל PR; פרסום ל־Pages רק אחרי מיזוג ל־`main`.

3. **מיגרציית מסעדת החיות** לתבנית משחק, עם גרפיקה ואנימציות ראשונות, תוכן JSON, שתי רמות הגיל, וקבצי קול סטטיים למשפטים (אם מאור יאשר). זה המשחק הראשון שמרגיש כמו "משחק אמיתי".
4. **מפת עולם** ופינת פנאי (בועות), ואחר כך עוד משחק אחד בבית השפות.
5. **גינת המספרים** — משחק כמות ראשון, אחרי שיש שתי תבניות יציבות (בחירה/הגשה ומיון/גרירה).
6. **מעבדת הטבע** ו**סטודיו יצירה** — לפי מה שהבנות נהנו ממנו, לא את כל הרעיונות בבת אחת.
7. **הקלטות איכות** למשחק הדגל ולמשפטים שכבר יציבים, אם שלב 3 התחיל ב־TTS מעבדתי.
8. בהמשך החזון, לא בפיילוט: שליטה בתוכן המכשיר, טווח גילים רחב יותר, וגיבוי בין מכשירים.

קריטריון איכות לכל שלב: הילדה מבינה מה לעשות בלי לקרוא, נהנית לחזור, הצבירה שקופה להורה, והמשחק עובד בטאבלט בלי רשת.

## 13. מה עודכן אחרי סקירות קלוד וג׳מיני

הסקירות הגולמיות: `docs/reviews/2026-11-10-claude-architecture.md`, `docs/reviews/2026-11-10-gemini-architecture.md`.

נקודות שאימצנו לשני המסמכים: הפרדת precache של השלד מ־runtime cache של עולמות; כלל לא לרנדר עברית/BiDi על קנבס Phaser; משפטים שלמים בתוכן JSON ואימות סכימה ב־CI; סימון P0 ב־`WORLDS.md`; תוכנית rollback וצורך באישור admin לשינוי Pages; מגבלות שעון המכשיר ומחיקת נתונים; מיגרציית סכימת אחסון; האזנה אינה idle; חלון חסד בסיום פנאי; הגבלת אתלס ל־2048; טיפול במחוות שוליים, multi-touch ו־CI של Playwright; וקידום קול סטטי כהצעה כבר במשחק הדגל.

### אי־הסכמות בין הסוקרים, ומה הוחלט במסמך

1. **מספר התקרות.** ג׳מיני המליץ לצמצם ל־3 פרמטרים הוריים; קלוד לא דרש זאת והתמקד במגבלות השעון ובסכימה. המסמך שומר את המודל מהחזון כהצעה, ומבקש ממשק הורה פשוט עם שדות מתקדמים מוסתרים. מאור יכריע.
2. **מתי נכנס קול סטטי.** קלוד הדגיש כשלים של TTS במכשיר; ג׳מיני המליץ לארוז קבצים כבר במיגרציית המסעדה. אימצנו את המלצת ג׳מיני כהצעה, בלי לבטל הקלטה אנושית כשלב איכות.
3. **היקף הפיילוט.** ג׳מיני הציע לצמצם את המסמך עצמו לשתי תבניות ועולם אחד; קלוד הציע לסמן P0 בתוך מפת החזון. אימצנו את גישת קלוד: המפה נשארת, עם סימון סדר ברור.
4. **טלמטריה.** קלוד העלה לוג שגיאות מקומי כחור; ג׳מיני לא דרש זאת. לא מוסיפים איסוף שגיאות, גם לא מקומי, בלי אישור מאור.
