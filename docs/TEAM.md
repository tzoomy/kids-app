# צוות הפיתוח ואופן העבודה

סטטוס: רוב סדר העבודה הוא **הצעה — ממתין לאישור**. הכלים עצמם (קלוד קוד ו־Antigravity/Gemini על מחשב העבודה, `gh` מחובר למאגר `tzoomy/kids-app`) כבר זמינים. מאור מאשר כיוון, בודק עם הבנות, וממזג שינויים משמעותיים.

המאגר ציבורי. אין להעלות אליו סודות, מפתחות, שמות אמיתיים של הבנות, או נתוני שימוש.

---

## תפקידים

| תפקיד | מי | מה עושה |
|---|---|---|
| מנהל מוצר וראש צוות | Grok Bot (השיחה עם מאור) | כותב משימות, פותח Issues, מחלק עבודה, מסכם סקירות, מעדכן את מאור, ולא ממזג שינוי משמעותי בלי אישורו |
| מפתח ראשי | Claude Code (`claude`) | מממש משימות בענף ייעודי, יכול להפעיל תת־סוכנים בתוך המשימה, פותח או מעדכן PR, לא ממזג ל־`main` לבד |
| סוקר ארכיטקטורה, קוד ועיצוב | Gemini דרך Antigravity CLI (`agy`) | סקירה עצמאית לכל PR ולמסמכי יסוד, כולל קריאה של צילומי מסך וגרפיקה; לא מממש את אותו PR שאותו הוא סוקר, אלא אם התבקש תיקון נקודתי אחרי הסקירה |
| בדיקות אוטומטיות | GitHub Actions | יחידות, בנייה, וצילומי מסך בגודל טאבלט על כל PR |
| מאשר ומנסה בבית | מאור | מאשר תוכנית, ממזג שינויים חשובים, בודק בטאבלט עם הבנות, וקובע יחס המרה, תקרות וסדר עולמות |

חלוקת התפקידים **הצעה — ממתין לאישור**. אפשר להחליף: קלוד סוקר וג׳מיני מממש, או ששניהם מממשים משימות שונות במקביל, כל עוד אין שני סוכנים שכותבים לאותם קבצים באותו ענף בלי תיאום.

## סדר עבודה ב־GitHub

**הצעה — ממתין לאישור.**

1. **Issue אחד למשימה אחת.** בכותרת ובגוף: המטרה, מה בתוך ההיקף ומה לא, קריטריון סיום, וקישור למסמך הרלוונטי. משימה גדולה (למשל מעבר ל־Phaser) מפוצלת לכמה Issues.
2. **ענף לכל משימה.** שמות מוצעים: `docs/…`, `feat/…`, `fix/…`, `chore/…`. לא עובדים ישירות על `main`.
3. **Pull Request.** התיאור בעברית (מונחים טכניים יכולים להישאר באנגלית). ה־PR מקשר ל־Issue, מסביר איך לבדוק, ומציין אם השינוי נוגע לאתר החי אחרי מיזוג.
4. **סקירת Gemini.** אחרי שיש diff יציב (או כבר במסמך, כמו עכשיו), רצים `agy -p` עם הנחיית סקירה לקריאה בלבד. את הסקירה הגולמית שומרים תחת `docs/reviews/`. מתקנים מה שמשכנע, ומתעדים מחלוקות בגוף ה־PR או בסקירה מעודכנת.
5. **CI.** הבדיקות וצילומי המסך חייבים לעבור, או להיות מסומנים במפורש כלא רלוונטיים למשימת תיעוד.
6. **מיזוג.** שינוי משמעותי (מנוע, משחק, גרפיקה, התנהגות פנאי, אזור הורה, או החלפת האתר החי) ממתין לאישור מאור. תיקוני תיעוד קטנים או תיקוני CI יכולים להתמזג אחרי סקירה, אלא אם מאור יבקש לאשר גם אותם. **אין למזג את ה־PR הזה** — הוא מוגש לאישור בלבד.
7. **פרסום.** אחרי מעבר ל־Vite, מיזוג ל־`main` מפעיל בנייה ופרסום ל־GitHub Pages. עד אז האתר החי הוא קבצי האב־טיפוס בשורש `main`. אין לשנות אותם במשימת תיעוד.

אין לדחוף ב־`--force` לענף משותף, ואין לשכתב את `main`.

## איך מפעילים את הסוכנים

מהמחשב שבו מותקנים הכלים, בתוך המאגר, עם `PATH` שכולל את `~/.npm-global/bin` ואת `~/.local/bin` לפי הצורך.

- קלוד, משימת מימוש או סקירה:  
  `claude -p "…"`  
  לסקירה בלבד יש לכתוב במפורש: לקרוא, לא לשנות קבצים, ולהדפיס את הסקירה.
- ג׳מיני, סקירה או תכנון:  
  `agy -p "…" --dangerously-skip-permissions`  
  אפשר `--mode plan` לתכנון, ו־`--output-format text` (או `json`) לפלט יציב.

שני הכלים עובדים ללא ממשק, והתחברות GitHub היא אותה התחברות של `gh`. אין להדביק מפתחות בצ׳אט או ב־Issue.

## קובצי מוסכמות בשורש המאגר

- `AGENTS.md` — כללי עבודה לכל סוכן: אתר חי, פרטיות, ענפים, שפה.
- `CLAUDE.md` — דגשים לקלוד כמפתח ראשי.
- `GEMINI.md` — דגשים לג׳מיני כסוקר.

אם הכלל מופיע ב־`AGENTS.md`, אין צורך לשכפל אותו באריכות; הקבצים הייעודיים רק מוסיפים תפקיד.

## מה מצפים בכל PR משמעותי

- שינוי במקום אחד ברור, בלי ריפקטור חופשי מחוץ להיקף.
- בדיקות חדשות או מעודכנות כשיש לוגיקה (במיוחד מנוע הפנאי).
- צילומי מסך מה־CI כשיש שינוי חזותי.
- סקירת Gemini שמורה ב־`docs/reviews/` או מקושרת מה־PR.
- תיאור עברי קצר למאור: מה השתנה, איך בודקים בטאבלט, ומה נשאר פתוח.
